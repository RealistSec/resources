# Implementation Standards — 20260430 Tools Suite Rebuild

This note is the lightweight working contract for implementation agents rebuilding the seven tools in `/tools`.

## In-scope tool folders

- `ai-data-readiness`
- `data-transfer-time-estimator`
- `graphql-query-complexity-analyzer`
- `graphql-schema-design-documenter`
- `rate-limiting-visualizer`
- `raw-http-security-header-analyzer`
- `secrets-rotation-schedule-generator`

## Definition of done for every tool

Each tool is only done when all of the following are true:

- The app works as a standalone static mini app from its own folder.
- Primary outputs are generated by real browser-side logic.
- The rebuild adds **at least two worthwhile new features** beyond the current baseline.
- The tool has `README.md`, `docs/user-guide.md`, `docs/dev-guide.md`, and `docs/screenshot.png`.
- The tool has been wired into `../index.html` as part of the portfolio suite.
- Core flows are responsive, keyboard-usable, and reasonable offline.

## Architecture guardrails

- Prefer plain HTML/CSS/JS or other static assets that can be opened locally.
- Do not require a backend, database, login, or third-party API for the primary happy path.
- If remote lookups are optional, provide a useful local path or sample input so the tool still demonstrates real value offline.
- Keep processing local where possible: parsing, validation, scoring, transformation, export, comparison, and visualization should happen in-browser.
- Avoid placeholder analytics, random scores, fake charts, or canned result text.

## Shared UX and design language

Rebuild the suite as one product family, not seven unrelated experiments.

Minimum shared patterns:

- Consistent page shell: title, short context blurb, input area, results area, secondary help area
- Consistent form controls, spacing rhythm, card treatment, and button hierarchy
- Consistent states for idle, loading/processing, validation error, empty result, and success
- Consistent copy tone: direct, practical, low-fluff, security/developer-friendly
- Consistent accessibility treatment: semantic labels, focus visibility, contrast, and live region messaging where results update dynamically

Exact visuals may evolve, but agents should not invent a brand-new layout language per tool.

## Feature bar for “worthwhile new features”

Purely cosmetic changes do **not** count.

Examples that do count:

- New parser, validator, comparison mode, or export path
- Better scenario modeling or multi-input analysis
- Saved presets, sample inputs, or shareable state that improves real usage
- Visualization that explains results more clearly and is derived from actual inputs
- Bulk input support, side-by-side comparison, or remediation guidance tied to real findings

Examples that do not count on their own:

- Restyling only
- Renaming labels only
- Adding static explanatory text only
- Placeholder charts or fake scoring

## Docs contract per tool

### `README.md`

- What the tool does
- Primary use cases
- Key features, including the newly added ones
- How to open and use it locally
- Screenshot reference: `docs/screenshot.png`

### `docs/user-guide.md`

- Fast start steps
- Input expectations
- Main workflows
- Interpretation guidance for outputs
- Known limits or caveats

### `docs/dev-guide.md`

- High-level structure of the tool
- Where the primary logic lives
- How to extend the new features safely
- Manual verification notes
- Screenshot capture/update note

## Screenshot workflow

- Required screenshot path per tool: `docs/screenshot.png`
- Capture a realistic final state that demonstrates the rebuilt tool’s strongest workflow
- Avoid empty forms, placeholder outputs, or obviously fake data states unless the tool itself is an analyzer with bundled sample input
- Keep the screenshot aligned with whatever appears in `tools/index.html`
- Update alt text in `tools/index.html` when the screenshot or tool framing changes materially

## Portfolio integration expectations

`/tools/index.html` is part of the implementation scope.

For each rebuilt tool, confirm:

- Link target is still correct
- Card title matches the final positioning
- Category tag still fits
- Screenshot source points to `docs/screenshot.png`
- Alt text accurately describes the new UI/output

## Practical review checklist for implementation agents

- Does this tool do something real with user input?
- Are the two new features meaningful enough to mention in the README?
- Does it look and behave like it belongs in the same suite as the other six tools?
- Can a user understand results without opening the source?
- Is the portfolio card still accurate?
